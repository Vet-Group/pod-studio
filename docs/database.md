# Database conventions

Applies to `packages/db` from P1-02 onward. Sources: PRD §4, ADR 0001 (stack) and ADR 0002 (store-scoped permissions).

## Structure

| Path | Contents |
| --- | --- |
| `packages/db/src/schema/*.ts` | Drizzle schemas, one file per domain. `index.ts` exports all schemas |
| `packages/db/src/schema/columns.ts` | Shared columns: `id()`, `createdAt()`, `updatedAt()`, `timestamptz()` |
| `packages/db/src/ids.ts` | `newId()`, `ID_PATTERN`, `isId()` |
| `packages/db/src/migrate.ts` | `migrateDatabase()`: runs migrations with locking and order checks |
| `packages/db/src/client.ts` | `createDatabase()`: postgres.js pool with schemas |
| `packages/db/migrations/` | SQL files numbered `0000_...`, `0001_...` and drizzle-kit's `meta/` |

Apps import `@pod-studio/db` (or `@pod-studio/db/schema` when only tables are needed).

## Schema conventions

- **Primary keys**: an `id` column of type `text`, defaulting to `newId()` (a 21-character nanoid). Matches `Id` in `packages/contracts/schemas/common.schema.json` (`^[A-Za-z0-9_-]{8,40}$`); tests read the pattern directly from the contract file. Do not use `serial`, `uuid` or sequential IDs.
- **Names**: plural table names in `snake_case` (`users`, `stores`, `store_members`). `audit_log` is singular because it is a ledger. Columns use `snake_case`; TypeScript properties use `camelCase`. Foreign keys use `<singular_table>_id` (`user_id`, `store_id`).
- **Index names**: `<table>_<column>_idx`; unique indexes use `<table>_<column>_unique`. Foreign keys keep the names generated by drizzle-kit.
- **No Postgres enums or CHECK constraints**. Fixed values use `text` columns, with valid values defined in code (`GLOBAL_ROLES`, `ACTOR_KINDS`) and checked at the application layer. Changing the list does not require a migration.
- **Timestamps**: all timestamp columns use `timestamptz` (`timestamp with time zone`). `created_at` and `updated_at` are `NOT NULL DEFAULT now()`; Drizzle refreshes `updated_at` in every update statement it emits. Handwritten SQL must explicitly set `updated_at = now()`.
- **Do not delete data with history**. Users are blocked (`banned`), and stores will be archived. Foreign keys from `audit_log` use `restrict`, so deleting a user or store already recorded in the ledger fails. Purely dependent data (sessions, accounts) uses `cascade`.
- **Case-insensitive string matching** uses a unique index on `lower(col)` (for example, `stores.domain`). The app stores normalized values.
- **JSON** uses `jsonb` with `$type<...>()` for typing; defaults to `'{}'` rather than `NULL` when a value is always present.

## Current tables

| Table | Purpose |
| --- | --- |
| `users`, `sessions`, `accounts`, `verifications` | better-auth 1.7.6 tables (email + password, admin plugin). Properties match better-auth field names; P1-03 connects the adapter with `usePlural: true`. `users.role` is the global role, either `admin` or `member` |
| `stores` | Shopify stores: name, `*.myshopify.com` domain, `api_version`. Credentials move to a separate table in P2-05 |
| `audit_log` | Append-only ledger: who acted, on which store, what they did, and which request |

Store-scoped permissions (`store_members`, `store_member_permissions`, presets) arrive in P1-04, following ADR 0002.

## audit_log

- `actor_kind`: `user`, `agent`, `worker` or `system`. `actor_user_id` is the real person behind the action; workers and system jobs leave it empty rather than acting under someone else's identity.
- `action` is a dot-separated verb, for example `store.member.grant`. `target_type` + `target_id` identify the affected object; `data` contains details in `jsonb`.
- `request_id` and `ip` (`inet`, also accepts IPv6) are left empty when the action does not originate from an HTTP request. Do not invent values.
- Migration `0001` installs triggers that block `UPDATE`, `DELETE`, `TRUNCATE`. Correct errors by adding a new row. Any future retention cleanup job requires its own reviewed migration.

## Migrations

```bash
pnpm services:up
cp apps/web/.env.example apps/web/.env.local   # once; contains local values only
pnpm db:migrate        # apply pending migrations to the database in DATABASE_URL or PG*
```

When changing schemas:

1. Edit files in `packages/db/src/schema/`.
2. `pnpm db:generate --name <mo_ta_ngan>` generates a new SQL file. Review the SQL before committing.
3. For changes drizzle-kit cannot generate (triggers, functions, data), use `pnpm --filter @pod-studio/db exec drizzle-kit generate --custom --name <ten>` and write SQL in the empty file. Keep `--> statement-breakpoint` between statements.
4. `pnpm db:check` checks snapshots, then run `pnpm test`.

Rules:

- **Never edit a migration that has run anywhere.** `migrateDatabase()` compares hashes and stops if an applied file has changed. Add a new migration to make changes.
- **Forward only.** There are no down migrations. A rollback is a new migration that reverses the change.
- **Later-generated migrations must come later.** When two branches generate migrations, the branch merged later must delete its own files and regenerate them on `main`. Drizzle silently skips migrations with timestamps older than an applied migration; `migrateDatabase()` stops with a `would be skipped` error instead.
- Do not use `drizzle-kit migrate` or `drizzle-kit push`. `pnpm db:migrate` adds an advisory lock (two processes starting simultaneously will not execute the same DDL twice) and the checks above.
- History is stored in `drizzle.__drizzle_migrations`.

## Tests

- Integration tests create a separate database with `createTestDatabase()` (`tests/support/db.ts`), then run `migrateDatabase(d.connection)`. Do not share `pod_dev`.
- `packages/db/test/migrations.test.ts` checks: clean application to an empty database, reruns making no changes, three parallel processes applying migrations only once; no enums or CHECK constraints; `text` primary keys named `id`; all timestamp columns using `timestamptz`; unique, cascade, restrict; `audit_log` blocking updates and deletes; hash and order guards.
